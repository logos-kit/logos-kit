## 3. Bugs, ranked by severity

1. **High — a full testimonial stats page can invalidate a post after approval in committed S8.** **Verified:** `resolveTestimonial` chooses a page before the user reads the approval (`packages/client/src/actions/wallet.ts:98-112`); **HEAD** `submit_public` does no re-page after `recheck` (`git show HEAD:crates/wallet-engine/src/tx.rs`, `submit_public`; the corresponding current function starts at `crates/wallet-engine/src/tx.rs:643`). Scenario: another author fills the page at the 1,000-author boundary during approval; the old page is submitted and the post fails after a fee. Suggested fix: finish and commit the worktree's guarded re-page (`crates/wallet-engine/src/tx.rs:655-717`), then exercise two concurrent authors at the boundary and verify unchanged approval/fee cap. **Unknown:** whether that uncommitted fix covers every `index==count` race.
2. **High — an in-flight testimonial can be attached to the wrong selected account.** **Verified:** the account chip can call `selectAccount` while `phase === "approving"` (`modules/logos_kit_testimonial/qml/Main.qml:409-439`); it resets the phase/account (`:128-133`). The approval callback and `onStatus` use mutable root state (`:188-225`). Scenario: select B while A's approval is open; A's handle returns, then `refreshAccount`/rejection recheck B, potentially showing B as posted or hiding A's result. Suggested fix: freeze `{api, chain, program, author, handle}` per flow; disable selection until the request is resolved; ignore stale callbacks.
3. **High — an outcome-unknown faucet claim can stay in “checking” forever.** **Verified:** `refreshBalance` swallows read failures and never invokes the callback (`modules/logos_kit_faucet/qml/Main.qml:122-130`); the 30-check exit is inside that callback (`:179-202`). Scenario: sequencer stays unavailable after an ambiguous faucet response; timer keeps firing without ever moving to a recovery state. Suggested fix: count completed attempts and elapsed time outside the success callback; show an explicit unresolved outcome that retains the request key and gives a safe balance-check path.
4. **High — private outcome-unknown checks the private account, although the faucet paid a public account.** **Verified:** the engine chooses a public `via` target for private funding (`crates/wallet-engine/src/engine.rs:596-638`), but the app checks `root.account` (`modules/logos_kit_faucet/qml/Main.qml:132-154,185-194`). Scenario: faucet pays `via`, its response is lost, no shield handle is returned, and the private balance remains unchanged; the app eventually says it could not confirm, without telling the user where the funds landed. Suggested fix: return the funded public account or an opaque status handle and query that outcome; surface the public-funds recovery action.
5. **High — “included” is reported as success even when outcome is unknown.** **Verified:** the schema explicitly says included transactions may have unknown outcome (`protocol/src/schema/transaction.ts:60-69`). Testimonial, faucet shield and template only branch on `outcome === "failure"` (`modules/logos_kit_testimonial/qml/Main.qml:201-211`; `modules/logos_kit_faucet/qml/Main.qml:212-216`; `templates/basecamp-dapp/qml/Main.qml:77-85`). Scenario: a failed or unproven transaction is included, but the app displays “Posted”, “Funds arrived”, or a successful receipt. Suggested fix: require `outcome === "success"`; for unknown, re-read the testimonial record/target balance or display “included, outcome unconfirmed”.
6. **Medium — network changes and old promises can repopulate a new-network screen.** **Verified:** the SDK rebuilds `api` on `chain` change (`sdk/qml/LogosKit/LogosKit.qml:61-96`), while app reset/restore and reads have no generation token (`modules/logos_kit_testimonial/qml/Main.qml:50-61,109-163`; `modules/logos_kit_faucet/qml/Main.qml:39-51,98-130`; `templates/basecamp-dapp/qml/Main.qml:31-46`). Scenario: a slow testnet response resolves after the wallet changes to local; old session, feed or balance appears under the local badge. Suggested fix: increment an epoch on `onApiChanged` and check it in every callback; capture the old API and reject late data. Also clear template `phase`, `balance`, and pending watcher.
7. **Medium — the template loses a late send handle.** **Verified:** the SDK times out after 45 seconds, keeps the old API busy, and only forwards a late answer if the host supplies `onLateResult` (`packages/qml-bundle/src/facade.ts:64-75,149-192`). `LogosKit.qml` supplies no such callback (`sdk/qml/LogosKit/LogosKit.qml:84-96`); the template's rejection path sets idle (`templates/basecamp-dapp/qml/Main.qml:49-53,71-86`). Scenario: user takes over 45 seconds to approve; template says an error, then cannot recover the eventual handle or receipt. Suggested fix: expose `onLateResult` in QML, keep a pending/unknown sheet until the wallet answers, and bind recovery to proposal id/handle.

**Validation cross-check:** **Verified:** QML's byte counter, blank check, C0/C1-with-newline exception, listed hidden characters and trimmed username closely mirror the Rust limits (`sdk/qml/LogosKitUi/TextBox.qml:16-26`; `modules/logos_kit_testimonial/qml/Main.qml:91-104`; `programs/testimonial/core/src/lib.rs:148-182`). No concrete accepted-by-UI/rejected-by-program string was established; malformed UTF-16 surrogate handling remains **unknown** without a Qt-to-Rust round-trip.

## 4. Security findings

- **Verified, bounded link opener:** `lez_openExplorer` accepts exactly one validated 32-byte tx hash or decoded account, uses only a fixed testnet HTTPS base, invokes the OS opener with an argument array, and has one open per second (`crates/wallet-engine/src/service.rs:1520-1567,1985-2008`). I found no arbitrary-URL injection. **Inferred risk:** every caller can open a validated page without a grant; one malicious app can drive up to one browser tab a second, affecting the user's desktop. Consider an app-grant/user-gesture gate or stricter global budget; the one-second limit is only friction.
- **Verified:** `lez_chainId` exposes the current chain to any caller (`crates/wallet-engine/src/service.rs:353-358`). This is ordinary public network metadata and appears acceptable; it does not disclose keys or private balances. No change recommended.
- **Verified:** `ui_requestFunds` is owner-only because all `ui_` methods are gated (`crates/wallet-engine/src/service.rs:345-351,604`). A `pvt_` handle is derived with the supplied app name (`:1392-1399,1475-1493`), but the engine derives the true requester from the caller or the wallet UI relay and checks account grants (`crates/wallet-engine/src/engine.rs:399-409,565-584,617-629`). A direct app cannot use another app's handle to fund its private account through this path. **Residual:** the UI's `requester` trust depends on the Basecamp shell's attestation (`modules/logos_kit_wallet_ui/qml/LogosKitWallet/Store.qml:196-204,241-243`); the dev harness simulates it and is not that proof (`modules/logos_kit_wallet_ui/dev/app_harness.py:1-8`).
- **Verified:** the cached genesis-key faucet is keyed by sequencer URL, and only selected for zone `lez-local` with an HTTP loopback prefix (`crates/wallet-engine/src/service.rs:1400-1406,1496-1514,1969-1972`).
